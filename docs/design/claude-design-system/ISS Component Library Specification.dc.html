Composition Patterns

01 — How to read this specification

Components are split into Primitives — components with no dependency on other components — and Composites, which are built exclusively from primitives (Philosophy §04, "components over pages"). Every entry uses the same nine fields so an implementer or Copilot can extract a consistent contract regardless of which component they're reading. This v1.0 set covers the components needed to build the first reference screens; it is additive — new entries follow the same template.

02 — Primitive components

Button

Primitive · Action
Purpose

Triggers a single action. The only component authorized to carry the accent color as a fill.

When to use

Any user-initiated action with an immediate, nameable effect: Save, Run, Export, Confirm.

When not to use

For navigation between views (use Link or Tab), or when more than one action would compete for the same visual weight — demote all but one to variant=secondary or tertiary.

Anatomy
  • Container (padding, radius, focus ring)
  • Optional leading icon
  • Label (type.body, 500 weight)
  • Optional trailing icon (chevron, external-link)
VariantFillUsage
primaryaccent solidOne per view — the primary action
secondarysurface + borderSupporting actions alongside primary
tertiarytransparentLow-emphasis, inline, or repeated-in-list actions
destructivestatus.danger solidIrreversible actions only, always paired with confirmation
States

default · hover (fill +4% darken) · focus-visible (2px accent ring) · active · disabled (50% opacity, no pointer events) · loading (label replaced by inline spinner, width preserved to prevent layout shift)

Accessibility
  • Native <button>; never a styled <div>
  • Icon-only buttons require an aria-label
  • Loading state sets aria-busy="true" and keeps the accessible name unchanged
Token usage
--iss-color-accent--iss-space-3--iss-radius-2--iss-font-body-size--iss-motion-fast
Engineering notes

Lit: <iss-button> exposes variant, disabled, loading as reflected attributes; slots for leading/trailing icons. Angular wrapper forwards the same API as @Input()s — no logic duplicated between wrapper and element.

Usage example
<iss-button variant="primary" (click)="runAnalysis()"> Run analysis </iss-button>

Input

Primitive · Form
Purpose

Single-line text entry, the base for search, filters, and form fields.

When to use

Any free-text or single-value entry under ~80 characters.

When not to use

Multi-line content (use Textarea) or a constrained set of options (use Select).

Anatomy
  • Label (above, always visible — never placeholder-only)
  • Field container (border, radius)
  • Optional leading icon (e.g. search)
  • Helper text or error message (below)
VariantUsage
defaultStandard form field
searchLeading search icon, clear (×) affordance when populated
inlineBorderless, for table-cell editing
States

default · focus (2px accent ring, border becomes accent) · filled · disabled · readonly · error (border + helper text in status.danger) · success (rare — used only for validated critical fields)

Accessibility
  • Label always programmatically associated via for/id, never placeholder-as-label
  • Error text linked with aria-describedby; field gets aria-invalid="true"
Token usage
--iss-color-border--iss-color-accent--iss-color-status-danger--iss-space-3--iss-radius-2
Engineering notes

<iss-input> wraps a native <input> in its shadow root so browser autofill and form participation (ElementInternals) keep working; validation state is a prop, never computed inside the component.

Usage example
<iss-input label="Case ID" [(value)]="caseId" [error]="caseIdError"> </iss-input>

Select

Primitive · Form
Purpose

Choosing one (or several) values from a bounded, named list.

When to use

2–50 known options. Under 5 mutually exclusive options, prefer a segmented control or radio group for visibility of all choices at once.

When not to use

Free-text entry, or unbounded/searchable large datasets — use Combobox (search + select) instead.

Anatomy
  • Trigger (label, current value, chevron)
  • Popover list (elevation.2)
  • Option rows with selected-state check
VariantUsage
singleOne value; trigger shows the selected label
multiSeveral values; trigger shows a count once >1 selected
States

default · open · focus · disabled · error

Accessibility
  • Full keyboard support: arrow keys to move, Enter/Space to select, Esc to close
  • Follows the ARIA listbox pattern; trigger has aria-expanded and aria-haspopup
Token usage
--iss-color-border--iss-elevation-2--iss-space-2--iss-motion-base
Engineering notes

Popover positioning uses the platform's shared floating-position utility (not component-local logic) so every popover-based component — Select, Combobox, Menu — collides with the viewport the same way.

Usage example
<iss-select label="Status" [options]="statusOptions" [(value)]="selectedStatus"> </iss-select>

Checkbox & Radio

Primitive · Form
Purpose

Binary and single-choice-from-visible-set selection, always with all options visible at once.

When to use

Checkbox: independent on/off choices, including "select all" in tables. Radio: one choice from 2–5 mutually exclusive, always-visible options.

When not to use

Radio for more than ~5 options (use Select) or for a single yes/no toggle taking effect immediately (use Switch, not covered in v1.0).

Anatomy
  • Control (16px box or circle)
  • Label (click target includes label, not just the control)
StateNotes
unchecked / checkedChecked fill uses accent
indeterminateCheckbox only — "some but not all" in table select-all
disabled50% opacity on control and label
Accessibility
  • Native <input type="checkbox"/"radio"> under the hood; custom visuals layered via ::after, never replacing semantics
  • Radio groups wrapped in <fieldset>/<legend>
Token usage
--iss-color-accent--iss-color-border--iss-space-2
Engineering notes

Both share one internal control-primitive in Lit to keep check/radio visuals pixel-identical in weight and size; only the shape and grouping semantics differ.

Usage example
<iss-checkbox [(checked)]="row.selected"> Row: row.id </iss-checkbox>

Badge

Primitive · Status
Purpose

A compact, named status marker — the primary carrier of the four status colors (Foundations §02).

When to use

Table rows, cards, and list items that carry a discrete state: Open, Blocked, Needs review, Stale.

When not to use

Counts (use a plain numeral) or as a button — badges are never interactive.

Anatomy
  • Container (low-opacity status tint background)
  • Optional status dot
  • Label (type.micro, always a literal state name, never a raw enum value)
ToneMaps to
neutralsurface.2 / text.muted — default, informational
successstatus.success
warningstatus.warning
dangerstatus.danger
infostatus.info
Accessibility

Tone is never the only signal — the label text always states the status in words; color reinforces (Foundations §07).

Token usage
--iss-color-status-*--iss-space-1--iss-font-micro-size
Engineering notes

tone is a closed enum, not a free color prop — this is what prevents a product team from inventing a sixth status color.

Usage example
<iss-badge tone="warning">Needs review</iss-badge>

03 — Composite components

Card

Composite · Container
Purpose

Groups related content and actions into one visually distinct unit at elevation.1.

When to use

Summarizing a single record or metric inside a grid (dashboards, list-of-records views).

When not to use

As a generic wrapper for page sections — plain structural spacing (Foundations §03–04) handles that without adding a visual boundary that isn't meaningful.

Anatomy
  • Header (title, optional Badge, optional overflow menu)
  • Body (data, chart, or table snippet)
  • Optional footer (Button row, right-aligned)
VariantUsage
defaultStatic summary card
interactiveWhole card is a single click target to a detail view — cursor and hover elevation change accordingly
States

default · hover (interactive only, elevation.1 → elevation.2) · focus-visible · loading (skeleton) · error (inline error state replaces body)

Accessibility

Interactive cards are a single <a> or <button> wrapping the content, never a <div onClick>, so keyboard and screen-reader users get the same target sighted users do.

Token usage
--iss-elevation-1--iss-elevation-2--iss-space-4--iss-radius-2--iss-motion-fast
Engineering notes

Header/body/footer are named slots in Lit, not positional children — this is what lets Angular content-project into a Card without knowing its internal DOM order.

Usage example
<iss-card variant="interactive" (cardClick)="open(record)"> <span slot="header">record.name</span> <iss-badge slot="header" [tone]="record.tone">record.status</iss-badge> </iss-card>

Table

Composite · Data
Purpose

The default view for any list of structured records with more than a handful of comparable fields — the platform's primary "data first" component.

When to use

Comparing multiple records across shared attributes: case queues, analytics rows, configuration lists.

When not to use

A single record's own detail (use a Detail layout) or fewer than ~4 comparable attributes (a Card grid reads faster).

Anatomy
  • Header row (sortable column labels, optional select-all Checkbox)
  • Body rows (Checkbox, cells, row-level overflow menu)
  • Sticky header on scroll
  • Footer (pagination, row count)
VariantUsage
defaultComfortable row height, 44px
compactDense analytical views, 32px rows — meets the 32px minimum target size (Foundations §07)
States

default · row-hover · row-selected · sorted-column (indicator on header) · loading (skeleton rows) · empty (renders the shared Empty State pattern, never a bare blank table)

Accessibility
  • Semantic <table>/<th scope> markup — never <div> grids styled as tables
  • Sort state announced via aria-sort on the header cell
Token usage
--iss-color-border--iss-space-3--iss-space-4--iss-font-body-size
Engineering notes

Column definitions are data, not template markup (a columns: ColumnDef[] input) so Copilot-generated table screens differ only in data mapping, never in DOM structure.

Usage example
<iss-table [columns]="caseColumns" [rows]="cases" [(selected)]="selectedIds"> </iss-table>

Filter Bar

Composite · Control
Purpose

The single, consistent place users apply and see criteria narrowing a Table or dashboard — makes filter state visible per the "recognition over recall" rule (Philosophy §05).

When to use

Above any Table or data view with more than one filterable attribute.

When not to use

A single search-only view — a bare search Input is enough; introducing a Filter Bar for one field adds structure with nothing to organize.

Anatomy
  • Search Input (optional, leftmost)
  • Filter chips (each a Select or date-range trigger)
  • Applied-filter pills (removable, one per active criterion)
  • "Clear all" tertiary Button, shown only when ≥1 filter is active
States

default (no filters) · active (≥1 applied filter, pills visible) · loading (results updating — Table shows loading state, bar stays interactive)

Accessibility

Each applied-filter pill's remove control has an aria-label naming the specific filter removed (e.g. "Remove filter: Status = Blocked"), not a generic "Remove."

Token usage
--iss-space-2--iss-space-3--iss-color-accent--iss-radius-2
Engineering notes

Emits one normalized FilterState object rather than per-field events, so any consuming Table/dashboard subscribes to one contract regardless of how many filters it exposes.

Usage example
<iss-filter-bar [filters]="filterDefs" [(state)]="filterState"> </iss-filter-bar>

Drawer

Composite · Overlay
Purpose

Surfaces a record's detail or a focused task without leaving the surrounding list context — the platform's one sanctioned "go deeper without navigating away" pattern.

When to use

Reviewing or editing one record from a Table/list while keeping that list visible and scroll-positioned behind it.

When not to use

A task requiring its own URL/deep link, or content wider than ~640px — route to a full page instead.

Anatomy
  • Scrim (dismisses on click, per "reversible by default")
  • Panel, fixed edge (always the same edge platform-wide — right, per Philosophy §06)
  • Header (title, close control)
  • Scrollable body
  • Sticky footer (primary/secondary Button pair)
VariantUsage
viewRead-only detail, no footer actions beyond Close
editForm body, footer holds Save/Cancel
States

opening/closing (motion.slow slide) · open · dirty (edit variant — Close asks for confirmation per "reversible by default" only when unsaved changes exist)

Accessibility
  • Focus moves into the drawer on open and returns to the triggering element on close
  • Focus is trapped within the drawer while open; Esc closes it
  • Root has role="dialog" and aria-labelledby pointing at the header title
Token usage
--iss-elevation-3--iss-motion-slow--iss-space-6
Engineering notes

One shared Lit host manages the scrim, focus trap, and animation; Table and Card interactive-click both open the same host so drawer behavior can never drift between entry points.

Usage example
<iss-drawer variant="edit" [open]="drawerOpen" (closed)="drawerOpen=false"> <span slot="header">Edit case: case.id</span> </iss-drawer>

System State Pattern

Composite · Feedback
Purpose

One shared pattern for the three states every data view eventually shows instead of its normal content: Empty, Loading, and Error — so users learn the pattern once, not three times per product.

When to use

Any Table, Card grid, or dashboard region whenever it has no data to show, is fetching data, or fetching failed.

When not to use

A first-run product tour or marketing empty state — this pattern is deliberately plain and functional, not a moment for illustration or personality (Philosophy §02).

Anatomy
  • Icon or skeleton region (functional, not decorative)
  • Message (states what happened, in the state's literal terms)
  • Optional single action (e.g. "Adjust filters," "Retry")
VariantMessage patternAction
empty"No records match the current filters."Clear filters (if any are active)
loadingSkeleton rows/cards matching the real layoutNone
error"Couldn't load records. Reason follows."Retry
Accessibility

Loading state's region has aria-busy="true"; error state's message is announced via a live region so screen-reader users don't have to discover the failure visually.

Token usage
--iss-color-text-muted--iss-space-8--iss-font-body-size
Engineering notes

Implemented as one <iss-state> component with a status input, not three separate components — this is what keeps their spacing and copy tone from drifting apart over time.

Usage example
<iss-state *ngIf="cases.length === 0" status="empty" message="No cases match the current filters." action-label="Clear filters" (action)="clearFilters()"> </iss-state>

04 — Governance

A new component enters this specification only when a real screen needs it and no existing primitive or composite already covers the need (Philosophy §04, consistency over novelty). Adding a variant to an existing component is preferred over introducing a new one. Any addition follows this same nine-field template and is versioned with this document — a v1.1 component addition does not require product teams to migrate anything already shipped against v1.0.
