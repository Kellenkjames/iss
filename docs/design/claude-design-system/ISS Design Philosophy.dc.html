Design Foundations

01 — Why this document exists

ISS is a suite, not a single application. Its users — analysts, operators, and builders working across case management, analytics, and automation surfaces — will move between products in the same session. If each product invents its own visual logic, that movement costs attention. This document exists so every future screen inherits the same reasoning instead of re-deriving it. It is deliberately not a style guide: colors and components come later, in Foundations and the Component Library. This is the layer underneath those — the reasoning that will make the tokens, components, and patterns cohere rather than accumulate as disconnected choices.

02 — Product personality

ISS should feel like a competent colleague, not a salesperson. Three traits define that:

Composed. The interface never competes for attention with the decision the user is trying to make. No motion, color, or copy exists to impress — only to inform.
Precise. Language and layout are literal. States are named for what they are (Blocked, Needs review, Stale) rather than softened or gamified.
Earned trust. The system shows its reasoning — data provenance, confidence, and what changed — rather than asserting conclusions. Trust is built through legibility, not confidence of tone.

03 — UX philosophy

Five commitments govern how ISS resolves any design decision, in priority order:

  1. Clarity over complexity. If a design requires a tooltip to explain itself, the design is wrong, not the tooltip.
  2. Consistency over novelty. A familiar pattern applied correctly beats a novel one applied once. Reuse is a design outcome, not a shortcut.
  3. Systems over screens. No screen is designed in isolation. Every layout is checked against the composition patterns it draws from before it is considered finished.
  4. Data first. Visual treatment supports comprehension of the underlying data — it does not decorate it. Charts, tables, and states are chosen for what they make legible, not for visual variety.
  5. Accessible by default. Contrast, focus order, and semantics are a property of the design at the moment it's specified, not a pass applied afterward.

04 — Information hierarchy principles

ISS interfaces are dense by necessity — technical users process large volumes of structured information. Density is acceptable; disorganization is not. Hierarchy is established through four ordered signals, used in this priority so pages stay legible without relying on color or weight alone:

01
Position — reading order and grouping carry more meaning than styling. Related data sits together before it is decorated.
02
Scale & weight — a small number of type sizes, used consistently, so a heading always reads as a heading across every product.
03
Structure — rules, spacing, and alignment separate sections before color does. Whitespace is a hierarchy tool, not empty space.
04
Color — reserved last, for status and one accent. It marks what needs a decision; it never distinguishes what is merely different.

05 — Cognitive load strategy

Cognitive load is treated as a budget every screen spends from, not an afterthought. Three disciplines keep the spend low:

Progressive disclosure. Default views show what's needed to act; detail is one deliberate click away, never buried further, never pre-loaded unasked.
One primary action per view. Secondary actions are visually and spatially subordinate. If a screen has three equally weighted actions, it is two screens.
Recognition over recall. Users should never need to remember a system's state — filters, applied criteria, and configuration are always visible where they take effect, not hidden after being set.

06 — Interaction philosophy

Interaction patterns are reused across products so muscle memory transfers. Three rules bound every pattern:

  1. Predictable over clever. The same gesture produces the same result everywhere in ISS — a drawer always opens from the same edge; a destructive action always confirms the same way.
  2. Motion communicates state, not personality. Transitions are short and functional — they show what moved and where it went. Motion that exists only to delight is out of scope.
  3. Reversible by default. Any action a user can take without confirmation must be undoable. Confirmation is reserved for the genuinely irreversible.

08 — What this governs next

Every subsequent artifact is a direct consequence of the principles above, not a separate decision:

02
Design Foundations — typography, color semantics, spacing, elevation, and motion, derived from the hierarchy and cognitive-load rules above.
03
Component Library — implementation-ready components mapped to Angular/Lit, each traceable to a value in Section 7.
04
Composition Patterns — reusable dashboard, workspace, and detail layouts assembled only from library components.
05
Reference Screens — worked examples proving the platform, not new design decisions.
