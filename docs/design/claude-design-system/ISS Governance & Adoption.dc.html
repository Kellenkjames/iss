01 — Why governance is its own phase

A design system decays the moment ownership is unclear — not through bad design, but through drift: a product team ships a one-off because no one owned the decision to say no, and the gap identified in a reference screen never gets fed back upstream. Phases 1–5 define what is correct; this phase defines who keeps it correct, and how it changes without fragmenting. Consistent with Philosophy §07 (long-term maintainability over short-term complexity), governance is not bureaucracy layered on top of the design — it is the mechanism that makes the design's own values enforceable.

03 — Versioning model

Every phase document versions independently but travels under one platform release number, so a product can state precisely which platform version it targets. Semantic versioning applies at both levels:

Change typeVersion bumpExample
MajorPlatform version (e.g. 1.x → 2.0)A token value changes in a way that breaks visual output (Foundations §08); a component's API changes incompatibly; a blueprint is removed or restructured.
MinorPhase version (e.g. Component Library 1.2 → 1.3)A new component or pattern is added (e.g. closing the iss-confidence-indicator gap from Reference Screens); an existing component gains a new variant without changing existing ones.
PatchPhase version (e.g. 1.2.0 → 1.2.1)Copy correction, accessibility clarification, non-visual documentation fix.

A major bump requires a written migration note in the changed phase document and a minimum notice period before any product is required to adopt it — no product is broken by an unannounced change.

04 — Change process (RFC)

Every change to Phases 1–5 — new token, new component, new pattern, or amendment — follows the same five-step path, regardless of who proposes it:

StepAction
01Propose — a written RFC citing the specific gap or need (a Reference Screens gap, a product team request, an accessibility finding), never a preference alone.
02Check for an existing pattern — the Platform Team confirms the need genuinely isn't covered by Phases 2–4 before treating it as new (per Philosophy §03, systems over screens).
03Draft to spec — authored in the same format as the relevant phase (e.g. a new component follows the Component Library's fixed spec: Purpose, When to Use, Anatomy, States, Accessibility, etc.).
04Review — Platform Team approves against the Design Values priority order (Philosophy §07); Engineering confirms implementability in Angular/Lit.
05Publish — merged into the phase document with a version bump and changelog entry; adopting products are notified per §03.

05 — Adoption model

Products inherit the system rather than implementing it independently, so conformance is structural, not a matter of discipline:

Tokens and components are consumed, not copied. Products import the shared token set and component library as a dependency; a forked copy is out of conformance by definition.
New products start from a blueprint, not a blank canvas. Every product's first screen must map to one of the four Composition Patterns blueprints (§2.2–2.5) before any custom layout work begins.
Conformance is reviewed at two points. A lightweight design review before build (blueprint + component selection) and a pre-launch audit against this document's phases — not a one-time gate at project kickoff only.
Copilot/AI-generated code inherits the same constraints. Generated UI code is expected to consume the same token and component contracts as hand-written code — the Component Library's engineering notes exist specifically so generated output is spec-conformant by construction, not by after-the-fact review.

06 — Deprecation policy

Removing a token, component, or pattern follows a fixed, reversible-feeling path rather than a sudden break — consistent with Philosophy §06's reversible-by-default stance applied to the platform itself:

StageMeaning
ActiveFully supported; recommended for new work.
DeprecatedStill functions; flagged in the spec with a replacement pointer; not to be used in new work. Minimum one minor-version cycle before removal.
RemovedDeleted from the spec at a major version boundary only, with the migration path published alongside the change per §03.

CadenceActivity

AnnualPhilosophy and Foundations reviewed for continued fit against the product portfolio — the only cadence permitted to touch Phase 1 or 2, given how much inherits from them.

08 — Closing statement

This document completes the ISS Design Operating System: Philosophy defines why, Foundations defines the raw material, the Component Library defines the parts, Composition Patterns defines the assembly, Reference Screens proves it, and this phase defines how it stays true over time. No future ISS product should need to make a foundational design decision — only to apply this system, and where it falls short, to name the gap and feed it back through the process above.
