Each is an architectural reference implementation — proof that Philosophy, Foundations, Component Library, and Composition Patterns compose into a working screen — not a new design decision. How to read this document

Each screen documents seven things: Purpose, Supported workflow, Component composition, Interaction rules, AI interaction, Engineering traceability, and Accessibility considerations. None introduce a component, token, or interaction not already specified in Phases 2–4 — each claim cites the section it draws from. A callout marks any point where the current system does not yet cover what the screen needs.

Screen 1 of 6
Dashboard

Signal Monitoring Overview — situational awareness for an operator starting a shift.

App Shell global bar
Primary trend chart — signal volume, 24h
KPI card — open cases
Signal feed — high priority
Signal feed — needs review
Status summary — system health
PurposeGive an operator a 10-second read on system state at shift start: what changed, what needs attention, nothing more.
Supported workflowMonitoring (Composition Patterns §03) — lands on default time range, anomaly surfaced via status color, drill-in opens List–Detail with dashboard state preserved on return.
BlueprintDashboard blueprint (Composition Patterns §2.3) — used as specified, three-column KPI/feed row beneath one primary trend region.
Component compositionApp Shell → Trend chart (data-display) → KPI card ×2 → Signal feed list (uses list-item + status badge primitives) → status summary using the four status tokens (Foundations §02).
Interaction rulesGlobal search and notifications live only in the shell (Composition Patterns §05) — the dashboard itself carries no local search. Drilling into a feed item follows the fixed cross-product handoff rule.
AI interactionFeed ranking is model-generated; each item shows a confidence indicator per AI pattern §06.1. No autonomous action taken from this screen — it is observation-only, consistent with human-in-the-loop default posture (§06.2).
Engineering traceabilityiss-app-shell, iss-trend-chart, iss-kpi-card, iss-list-item, iss-badge — all Component Library primitives/composites, no new elements.
AccessibilityTrend chart exposes a text-equivalent summary (value + delta) for screen readers — chart color alone never carries the trend direction, per Foundations §07 never-color-only rule.
Screen 2 of 6
List–Detail Workspace

Case Queue — an operator triages and works assigned cases.

App Shell global bar
Filter chips + sortable case list, priority-ordered
Case detail — fields, history, primary action top-right
PurposeLet an operator move through a prioritized case queue, inspect one case in full, and act — without losing place in the queue.
Supported workflowCase management (Composition Patterns §03) — queue sorted by priority/SLA, claim, work in detail pane, explicit status change.
BlueprintList–Detail (§2.2), one list / one detail / one action zone per Composition rule §04.
Component compositionFilter chip row (removable, visible per §04 "filters live where they act") → list-item rows with status badges → detail panel using field/label primitives and a fixed-position primary action button.
Interaction rulesArrow keys move list selection, Enter opens detail, Esc returns to list (cross-app keyboard standard §05). Scroll position and filters persist on return from detail, per state-survives-navigation rule.
AI interactionQueue order is a model-ranked suggestion (priority score); confidence shown per case. Case status changes always go through Review & decide — no case auto-closes without an explicit user action.
Engineering traceabilityiss-filter-chip, iss-list-item, iss-badge, iss-detail-panel, iss-button (primary) — all existing library components.
AccessibilityList is a proper listbox role with roving tabindex; selected row is both visually and semantically marked (aria-selected), not color-only.
Screen 3 of 6
AI Review Workspace

Signal Review — an analyst evaluates a model-flagged signal and commits a decision.

Primary artifact — signal detail, evidence, source data
Context panel — confidence, "why" evidence links, decision controls
PurposeGive a human reviewer everything needed to accept, edit, or reject a model-generated suggestion, with the reasoning behind it inspectable, not asserted.
Supported workflowReview & decide (Composition Patterns §03) — open item, system presents evidence/confidence, user accepts/edits/rejects, override reason logged.
BlueprintWorkspace/Review (§2.4) — primary artifact left, context + decision controls right.
Component compositionDocument/signal viewer (primary artifact) → confidence indicator component → "why" disclosure (progressive disclosure primitive) → decision control group (accept / edit / reject) with reason field on override.
Interaction rulesOnly one primary action (commit decision) is fixed top-right of the context panel; edit and reject are secondary, per singular-primary-action rule (§04). Rejecting an AI suggestion is reversible until commit — no confirmation needed until commit itself, which is irreversible.
AI interactionAll four remaining AI-native patterns apply directly: confidence is always visible (§06.1), reasoning is inspectable via the "why" disclosure (§06.3), and any override is logged as data attached to the record, not a transient UI event (§06.5).
Engineering traceabilityiss-signal-viewer, iss-confidence-indicator, iss-disclosure, iss-decision-controls, iss-text-input (override reason).
AccessibilityConfidence indicator pairs a numeric/label value with color, never color alone; decision controls are reachable and operable via keyboard with clear focus order (evidence → confidence → decision).
Gap identified: the Component Library does not yet specify a iss-confidence-indicator component. It is described functionally in Composition Patterns §06.1 but has no Purpose/Anatomy/States spec. Recommend adding it to the Component Library as a Composite Component before this screen is implemented.
Screen 4 of 6
Configuration

Alert Rule Settings — an admin adjusts thresholds for a signal-detection rule.

Section nav — steps: General / Thresholds / Notifications
Narrow form column (720px) — field groups, change summary before commit
PurposeLet an admin make an infrequent, deliberate change to system behavior with full visibility into what will change before it takes effect.
Supported workflowConfiguration change (Composition Patterns §03) — locate setting, change inline, review change summary, confirm only if irreversible.
BlueprintConfiguration (§2.5) — the one blueprint using the 720px narrow container per Foundations §04, since this is a linear, form-first task.
Component compositionStep/section nav (tabs) → form field group primitives (label, input, select, toggle) → change-summary component (diff of prior vs. new values) → commit button.
Interaction rulesReversible field edits require no confirmation; committing recalculates downstream alert behavior and is treated as irreversible, so it uses the standard destructive/impactful confirmation copy pattern (§05).
AI interactionNot applicable — configuration is a deterministic human action by design; no AI-native pattern applies here, consistent with human-in-the-loop being the default and full autonomy requiring separate approval (§06.2).
Engineering traceabilityiss-tabs, iss-field-group, iss-toggle, iss-select, iss-diff-summary, iss-button, iss-confirm-dialog.
AccessibilityEvery field has a programmatically associated label; step nav is operable via keyboard with current step announced; change summary is structured text, not an image, so it's screen-reader legible.
Gap identified: a iss-diff-summary component (structured before/after change list) is implied by the Configuration workflow's "review a summary of what changed" step but is not yet specified in the Component Library. Recommend adding it as a Composite Component.
Screen 5 of 6
Search Workspace

Cross-Product Search — a user finds a record without knowing which product owns it.

Facet filters — grouped by product
Results grouped by product, ranked within group
PurposeResolve a query to the right record in the right product in one search, without the user needing to know product boundaries in advance.
Supported workflowSearch & filter (Composition Patterns §03) — enter criteria, results update in place, refine without losing scroll position, select opens detail.
BlueprintList–Detail (§2.2), specialized: the "list" side is grouped results rather than a single collection, per the global-search rule in §05 that results are grouped by product, never mixed unlabeled.
Component compositionGlobal search input (from App Shell, §05) → facet filter group → result-group header + list-item rows reused from List–Detail. Selecting a result performs cross-product handoff (§05) into that product's native List–Detail context.
Interaction rulesIdentical keyboard bindings to List–Detail (arrow/Enter/Esc) so the pattern transfers. Filters remain visible chips, not a reopened panel.
AI interactionResult ranking may be relevance-model-driven; confidence/relevance is shown per §06.1 only where the ranking is model-generated rather than exact-match, so literal matches aren't given a spurious confidence score.
Engineering traceabilityiss-search-input, iss-filter-chip, iss-list-item, iss-group-header — all existing components; no new primitives required.
AccessibilitySearch input has an accessible name and live-region announcement of result count on update, so screen-reader users get the same "results updated in place" feedback sighted users see.
Screen 6 of 6
System States

Loading, Empty, and Error — the non-happy-path states every workflow above must specify.

Loading — skeleton rows + literal status copy
Empty — icon-free message + one recovery action
Error — cause + retry, never a bare failure
PurposeProve that every blueprint's non-happy-path is a designed state, not an accidental blank screen — the explicit requirement of Composition Patterns §04.
Supported workflowApplies across all five workflows in §03 — every list, detail, and dashboard region substitutes one of these three states for its content region when applicable.
BlueprintNot a standalone blueprint — an overlay state applied within any of the four blueprints' content regions.
Component compositionLoading: skeleton primitive matching the region's real layout, plus literal progress copy for AI-driven waits (§06.4, e.g. "Analyzing 240 records…"). Empty: status-view component, message + single recovery action. Error: status-view component, cause + retry action, never a bare failure.
Interaction rulesA region never shows a bare spinner with no text for an AI-driven process (§06.4). Retry from an error state must not discard user-entered filters or criteria that led to it.
AI interactionLong-running AI generation (streaming summary, running analysis) uses the loading state with literal, updating status text rather than an indeterminate spinner, per §06.4.
Engineering traceabilityiss-skeleton, iss-status-view (empty/error variants) — both specified in the Component Library's status-view spec (Component Library, feedback components).
AccessibilityLoading state changes are announced via an aria-live region; error status-view text is not conveyed by icon or color alone and is focusable so screen-reader users land on it immediately after a failed action.

Summary of identified gaps

Two components are referenced functionally by the Composition Patterns but not yet formally specified in the Component Library: iss-confidence-indicator (Screen 3) and iss-diff-summary (Screen 4). Both should be added to the Component Library specification before their respective reference screens are implemented — per this platform's own rule, a gap is named and fed back upstream, never patched locally.
