01 — Purpose of this layer

The Component Library specifies correct pieces; it says nothing about correct arrangement. Left unconstrained, every product team would assemble those pieces into a different shell, a different filter pattern, a different confirmation flow — reintroducing the inconsistency the Design Platform exists to remove (Philosophy §03, Systems over screens). This document is the missing layer: a fixed set of application layouts, canonical workflows, and cross-app interaction rules that every ISS product composes from rather than invents. Nothing here is a mockup — each pattern is a structural contract a real screen must satisfy, not an example to imitate loosely.

03 — Canonical workflows

These five task shapes recur across every ISS product. Each maps to one layout blueprint and a fixed interaction sequence — a product implements the sequence, not a variation of it.

WorkflowBlueprintCanonical sequence
Search & filterList–DetailEnter criteria → results update in place → refine without losing scroll position → select a result opens detail, filters remain visible
Review & decideWorkspace/ReviewOpen item → system presents evidence/confidence → user accepts, edits, or rejects → decision is logged with a reason when overriding a system suggestion
Case managementList–DetailQueue sorted by priority/SLA → assign or claim → work the case in detail pane → status change is explicit, never inferred from navigation
Configuration changeConfigurationLocate setting → change value inline → review a summary of what changed before committing → confirm only if the change is irreversible (Philosophy §06)
MonitoringDashboardLand on default time range → identify anomaly via status color → drill in opens the List–Detail workflow for that signal, dashboard state is preserved on return

04 — Composition rules

Rules that govern how any product assembles library components into the blueprints above, regardless of domain:

One list, one detail, one action zone. A List–Detail screen never nests a second list-detail pair inside its detail pane — drill-down navigates, it doesn't nest.
Filters live where they act. Applied filters render as visible, removable chips beside the results they affect — never collapsed into a panel the user must reopen to recall (Philosophy §05, recognition over recall).
Primary action is singular and fixed in position. Every blueprint reserves one consistent location (top-right of the detail/context pane) for the one primary action; secondary actions go in an overflow, never compete visually.
State survives navigation. Scroll position, filters, and selection persist when a user drills in and returns — a workflow interrupted by navigation is a design defect, not an acceptable tradeoff.
Empty, loading, and error states are designed, not defaulted. Every list/detail/dashboard region specifies its own empty and error state per the Component Library's status-view spec — a blank div is never shipped as a fallback.

05 — Cross-application interaction standards

These behaviors are identical across every ISS product so a user's muscle memory transfers when they switch tools mid-session:

InteractionStandard
Global searchSame shortcut and position in every product (App Shell global bar); results are grouped by product, never mixed unlabeled
NotificationsOne global notification center in the shell; a product never runs its own separate notification surface
Keyboard navigationArrow keys move list selection, Enter opens detail, Esc closes overlays — identical bindings in every list-detail surface
Destructive confirmationSame confirmation dialog pattern and copy structure ("This will —, and can't be undone.") everywhere an irreversible action exists
UndoReversible actions surface a transient undo affordance in a fixed shell location, not a per-product toast style
Cross-product handoffLinking to a record in another ISS product always opens it directly in that product's List–Detail context, never a generic external redirect

06 — AI-native interaction patterns

ISS is AI-native, not AI-decorated — every workflow above that involves a system judgment (a suggested action, a ranked result, a generated summary) follows the same four patterns, so users learn to read machine involvement once and reuse that understanding everywhere.

Confidence is always visible, never implied. Any AI-generated ranking, score, or summary carries an explicit confidence indicator using the Component Library's status tokens — a bare number or unlabeled color is not sufficient.
Human-in-the-loop is the default posture. The system proposes; the canonical Review & decide workflow (§03) is the only path by which an AI suggestion becomes a committed action. Full autonomy is an explicit, separately-approved exception per product, not a default.
Reasoning is inspectable on demand. Every AI output exposes a "why" affordance (source evidence, contributing signals) one click away — progressive disclosure per Philosophy §05, not surfaced unasked, never withheld entirely.
Generation state is legible. In-progress AI work (streaming summary, running analysis) uses the Component Library's loading states with literal status copy ("Analyzing 240 records…") — never a bare spinner standing in for unexplained system activity.
Overrides are logged as data, not hidden as UI state. When a user rejects or edits an AI suggestion, that correction is captured with the record (per Component Library audit-trail patterns) — it is product data, not a transient interface event.

07 — What this governs next

Reference Screens (Phase 5) are worked examples that apply every blueprint, workflow, and rule above to real ISS product scenarios — they exist to prove this specification, not to introduce new layout or interaction decisions. Any screen that cannot be built from this document's rules is a signal to amend this document, not to improvise around it.
